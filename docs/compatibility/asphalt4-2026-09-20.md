# Asphalt 4 1.2.0 — invisible drawable and sound-loading crash

## Result

Installed Asphalt 4 1.2.0 in simulator LiveContainer and fixed the persistent
blank game surface after the intro. Two clean URL launches with the final
storage-only patch reached the visible, upright language menu without debugger
intervention.

This is not a full playability result. The approximately 41-second intro still
has no visible video, and gameplay and the real device have not been retested.
No MediaPlayer presentation change is included in this patch.

Follow-up: the user found a crash after **English → Yes (enable sound)**; choosing
sound off worked. LLDB confirmed a missing `AudioFileStreamOpen` export. The
streaming-audio bridge is now implemented and deployed to this game's isolated
simulator runtime, with parsing regressions passing. The post-fix sound-enabled
game interaction is awaiting user confirmation.

## Rendering diagnosis

After fixing the installation path, the baseline still displayed black after
the intro even though the game was drawing its language menu:

- The visible window contained a `UIGLView` backed by `CAEAGLLayer`.
- Rendering occurred on a game worker thread, with an OpenGL ES 1 context.
- Viewport: `320 x 480`; framebuffer and renderbuffer names: `1`.
- Framebuffer status: complete (`0x8cd5`); `glGetError()`: `0`.
- RGBA8 framebuffer readback contained **150,158 non-black pixels out of
  153,600**. The drawable had a `CAImageQueue`, but the screen remained black.
- Calling **`[CATransaction flush]` on the rendering worker** immediately made
  the language menu visible.

This isolates the persistent blank surface to an uncommitted Core Animation
transaction, not missing assets, a failed framebuffer, or black GL output.

## Change

In `HostFrameworks/OpenGLES/OpenGLES.mm`, the existing drawable-storage adapter
now flushes Core Animation after successful layer-backed storage creation on a
non-main thread. This publishes the drawable image queue even when the game's
render thread does not run a run loop to commit its implicit transaction.

The flush also covers storage reallocation and follows the existing RGB565
fallback. Failed storage, non-layer drawables, and main-thread callers are
unchanged. There is no per-frame presentation hook or game-specific check.

## Sound-loading crash

On the user's reproduction, LLDB stopped on the game worker in
`LC32ThrowGuestCrashException` with:

```text
Signal: SIGABRT (6)
Guest error: Symbol not found: _AudioFileStreamOpen
Expected in: /System/Library/Frameworks/AudioToolbox.framework/AudioToolbox
ASPHALT4`SoundEngineEffect::AttachFilesToSource() [call at 0x61714]
ASPHALT4`SoundEngine_LoadEffect [call at 0x5f4c0]
```

This is a missing streaming-file parser API used to load effects, separate from
the GL transaction issue and from whether the simulator can produce OpenAL
audio. No sound-disable workaround is applied.

The AudioToolbox bridge now exports `AudioFileStreamOpen`, `ParseBytes`,
`GetPropertyInfo`, `GetProperty`, `Seek`, `SetProperty`, and `Close`. It uses the
native parser with opaque guest tokens, synchronous guest property/packet
callbacks, copied callback buffers, and mutable property-flag copyback. Property
queries can re-enter the parser from a callback. Closing inside a callback
invalidates the token immediately and defers native destruction until parsing
unwinds. A recursive parse is rejected instead of re-entering native parsing.

The bridge handles ARM32 structure strides for format lists and frame/packet
translations, one-byte `Boolean` output, and 64-bit seek offsets. Supported
properties are fixed-width/POD values. `InfoDictionary` and unknown properties
explicitly return unsupported rather than copying native object pointers.

Audio verification:

- Guest and host framework builds passed; all seven exports are present.
- New `test/audio_file_stream.c`: **202 PASS checks, zero failures**, executing
  as ARM32 through the isolated runtime. Covers whole WAV input, fragmented WAV
  on a guest pthread, callback-time property queries, PCM byte equality, output
  canaries, frame/packet translation, seek width, stale tokens, close inside a
  callback, and fragmented AAC with packet descriptions and format-list ABI
  conversion. The same portable cases also passed against native AudioToolbox.
- WAV format-list retrieval is unavailable in the native parser and is reported
  as a skip; the generated AAC fixture exercises that property successfully.
- Existing runtime regressions passed: audio converter **5**, extended audio
  file/wrapped callback file **64**, and audio-file creation/packet reads **12**
  PASS checks. All guests exited with code 0.
- `git diff --check` passed. The simulator has both the new guest AudioToolbox
  and shared host runtime; other games' emulator selection remains unchanged.
- On September 21 the user confirmed the English → Yes (sound enabled) retest
  works. The test debugger has since been detached and closed. This confirms
  the reported sound-loading crash is fixed, not a full gameplay/audio audit.

## Remaining intro issue

The guest's `-[MoviePlayer playMovie]` calls native `-[MPMoviePlayerController
play]` and sets its playing flag; it does not attach the movie view or create a
presenting controller. At the native play breakpoint, execution was on the game
worker and both the movie proxy view and hosting controller were nil.

That usage depended on the old automatic fullscreen behavior documented in
Apple's [archived movie playback guide](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/MultimediaPG/UsingVideo/UsingVideo.html).
The native player reports a duration of **40.68 seconds**. Natural completion
does let the game continue to its menu in clean runs, but the video is invisible.

Diagnostic attempts to set fullscreen or attach the proxy view did not establish
a working, self-cleaning presentation fix. A separate legacy movie-presentation
adapter needs verification, including completion and skip cleanup, before it is
safe to include. The current patch fixes the persistent GL blank screen only.
